01 / 核心观点

先把“自我改进”定义清楚

RSI 不是单一算法，也不是“模型多想几遍”。本文把它定义为：一个 AI 系统在多轮运行中，利用自身或外部反馈，更新其可影响后续性能的组件，并在相对独立的任务/环境上验证改进。更新对象可以是输出策略，也可以是记忆、工具、代码、权重、数据、评估器，乃至选择研究问题的流程。

不算 RSI 的情况

一次性自我反思（self-reflection）、固定提示链（prompt chain）、只在同一道题上重采样、没有跨任务或跨轮次积累的“看起来更聪明”。

最低证据标准

改进前后要有冻结的外部测试集、明确的更新对象、完整轨迹、成本与失败统计，并排除评估器泄漏（evaluator leakage）和基准过拟合（benchmark overfitting）。

现有工作卡在哪一层

把"框架会变化"拆成三层，才能说清楚谁做过什么。绝大多数被称作 RSI 的工作只动了第一层；第二、三层各只被做了一半，而且都不是由系统自己驱动的。

第 1 层 · Content内容演化

组件里的代码、提示词、权重变了，但有哪些组件、怎么连不变。STOP、Gödel Agent、DGM、HGM 全在这层。

第 2 层 · Composition组成演化

系统由哪些组件构成、每个组件允不允许被改。AgentSquare 做了一半——模块可换，但"就是这四类"是人定的。

第 3 层 · Topology拓扑演化

组件之间怎么连、执行顺序、谁控制谁。AFlow 做了一半——图结构可搜，但算子表是人给的。

结构自由度到底值不值？

正反都能发

问题：允许改组成/拓扑，比只改内容，在同等预算下多赚了什么？

  1. 同任务、同模型、同 token 预算，三组对照：只改内容 / 可增删组件 / 可改连接与顺序。
  2. 主指标：隐藏集增益 ÷ 单位算力。
  3. AFlow 与 AgentSquare 都假定结构搜索有用，但没人把它和"只改内容"在同算力下对比过。
这是整个方向的前提 · 若答案是"不值"，后面所有设计都要变

03 / RSI 评测基准

RSI 到底该怎么测？

截至 2026 年 8 月，尚没有一个被广泛接受、能完整衡量递归自我改进的统一基准。关键不是再造一个排行榜，而是把“系统如何利用反馈改自己”和“改完后是否真的变强”拆开测。

先纠正一个容易混淆的前提：目前没有公认的 RSI base agent，也没有唯一的“后继系统必须怎样接管”的实现。强 RSI（strong RSI）要求后继系统继续产生下一代；现有工作还包括固定元智能体、档案式进化和组件级自适应。benchmark 应声明测哪一种，并把规则、执行基础设施和被测改进算法分开。

三层必须分开：定义协议、运行 harness、被测 RSI 框架

动态 benchmark 确实需要软件来运行多代系统，但 harness 只执行规则；一旦它决定如何生成、选择或修改后继版本，它就成为被测方法的一部分。

规则层 · ProtocolRSI 评测协议

规定“自我”的边界、可修改组件、反馈可见性、代数、预算、隐藏任务、停止规则和指标。它回答“什么证据算改进”。

执行层 · Harness中立运行与留证

启动容器、交接后继制品、隔离 evaluator、记录哈希和谱系、执行预算与回滚。它不替参赛系统提出修改。

方法层 · Framework被比较的 RSI 系统

固定元智能体、单链自改、DGM/HGM 式档案搜索、记忆或数据自进化都可以接入。它们决定“如何改”。

被测系统 S_t = 任务智能体 A_t + 改进器 U_t + 持久状态 K_t　｜　U_t(A_t, K_t, feedback) → (A_t+1, U_t+1, K_t+1)

弱模式：固定改进器

U₀ 每一代都负责修改任务智能体。可以测自动智能体开发，但不能证明改进器自身变强。

MAC 更接近此类

中间模式：档案进化

从多条 lineage 选择父代并产生后代。可以研究长期生产力，但外层选择器和效用通常仍是固定的。

DGM / HGM 类

强模式：后继接管

U_t 也被继承或修改，并由后继系统产生下一代。它是强 RSI 的可测条件，不是当前唯一公认架构。

重要开放问题

普通基准与 RSI 基准，差别不只是“测一次还是测两次”

普通基准也可以有开发集（development set）和测试集（test set）。RSI 的特殊之处是：系统反复读取环内反馈，并据此产生下一代系统，因此评价本身成为了学习过程的一部分。

普通基准与 RSI 评测协议对比
比较项普通/静态基准（Conventional benchmark）RSI 评测协议（RSI evaluation protocol）
被测对象（Object）一个相对固定的模型或智能体，回答一组任务。基线系统、改进机制、连续候选版本及其完整谱系（lineage）。
适应轮次（Adaptive rounds）通常按固定配置跑一次或若干独立重复；分数不应在本次正式测试中驱动持久自修改。明确允许多轮“诊断→修改→评估→选择”，下一轮候选依赖上一轮反馈。
反馈的作用（Feedback effect）开发集可用于调参，但正式报告常聚焦最终测试分数。反馈是系统演化的输入，必须记录它如何改变后续版本，不能只展示胜出的最后一个点。
开发/搜索侧（Dev / search side）用于选模型、提示词或超参数。是正式被测机制的一部分：限制查询次数、预算、可见日志、可修改组件和停止条件。
隐藏/最终侧（Hidden / final side）估计固定系统在未见样本上的泛化表现。比较冻结基线与冻结最终候选的隐藏增益，并检验搜索过程是否产生可迁移的真实改进。
主要输出（Outputs）最终分数、置信区间、按任务切片结果。完整改进轨迹 + 最终隐藏增益 + 因果归因 + 成本/时间 + 安全事件 + 失败分支。
主要失真（Main threats）训练污染（contamination）、测试泄漏、抽样偏差。还增加自适应过拟合（adaptive overfitting）、评估器投机（evaluator gaming）、改分数而非改能力，以及无法归因增益。

关于 GroundBench：这里按 RHIO 论文提出的 GroundBench 理解，它汇集五个长文本问答（long-form question answering, LFQA）数据集，测上下文忠实性（contextual faithfulness）。它本身是普通的结果型基准，不直接测 RSI；但可以被嵌入 RSI 协议，作为环内任务集或隔离的环外任务集。只有加上多轮自修改、可见性契约、冻结候选和前后对照，它才成为 RSI 证据的一部分。[S14]

模型能看到什么，由谁规定？

没有一条自然法则规定“环内优化评估器一定公开”或“评分代码一定隐藏”。可见性是评测协议中的访问契约（access contract），由设计者声明、基础设施执行、审计者核验。

规则层（Specification）

1. 基准/协议设计者（Benchmark & protocol designer）

定义任务分布、开发与隐藏划分、模型/元智能体各自可见的信息、允许修改的组件、查询预算、停止规则和主指标。若研究者既设计又参赛，应预先注册协议并引入独立保管方。

执行层（Enforcement）

2. 环境与权限系统（Environment & access control）

通过容器、网络策略、只读挂载、受限 API、密钥、进程权限和时间锁真正落实契约。文字上说“不能看”不够，系统必须让读取或修改隐藏资产在技术上失败。

证据层（Evidence custody）

3. 评估基础设施（Evaluator infrastructure）

保管隐藏任务、答案、测试和评分日志，记录查询、镜像、随机种子、版本哈希与时间戳。开发预算结束后才挂载最终验证器，是一种可操作的时间隔离。

复核层（Independent review）

4. 独立审计者（Independent auditor）

检查是否泄漏、越权、替换评估器、挑选幸运种子或隐去失败谱系，并使用另一套任务、验证器或专家盲评复核结论。设计者规定契约，审计者判断契约是否可信地执行。

RSI 搜索阶段与隐藏阶段的信息可见性矩阵
信息/能力搜索阶段（Search phase）隐藏阶段（Hidden phase）为什么这样设计
当前任务输入（Task input）开发任务题面通常可见。最终候选在作答时当然能接收该题输入；但负责改系统的控制器（improvement controller）已经冻结，不能据此再发布新版本。区分“看见要回答的问题”和“看见答案后继续改系统”。
开发样例（Development examples）可见，并明确属于搜索数据。不再增加；不能把隐藏案例回流成新开发样例。防止自适应污染隐藏集。
聚合分数（Aggregate score）可见或限频返回，可加噪声/分桶。在候选冻结和运行结束后发布；发布后不得回到本轮改进。分数一旦驱动修改，就属于搜索信号。
失败日志（Failure logs）由协议配置：可给完整日志、错误类别或只给通过/失败。通常封存到最终结束；之后可用于分析，不用于重跑选优。控制反馈带宽（feedback bandwidth）和过拟合速度。
评分规则/代码（Rubric / scoring code）可以公开规则，也可以只开放 API；公开规则不等于公开隐藏案例。协议可公开抽象规则，但隐藏测试、密钥和逐题标签仍隔离。真正关键的是不可利用的隐藏实例与不可篡改执行，而非一概保密所有规则。
隐藏答案/测试（Hidden labels / tests）绝不应可见，也不可由侧信道推断。候选只接收必要输入；答案和断言由隔离执行器持有。这是环外证据成立的最低边界。
修改权限（Write access）只能改协议白名单中的提示词、记忆、工具、代码、数据或权重。候选版本、依赖和环境全部只读冻结。防止“测评时继续进化”以及修改测试/评分器。
外部审计（External audit）可以公开审计原则，但不开放具体新题与人工判定。由独立方执行；结果与方法在审计完成后发布。避免同一个评估器同时充当老师、考官和证明人。

具体例子：Meta-Agent Challenge（MAC）允许元智能体读取任务、编辑 agent.py 并查询开发集评估 API；测试集加密存放在另一容器中，开发预算结束后才挂载验证器。模型“看得到反馈”指 API 返回被允许的信息，不表示它能读取测试集、答案或验证器内部实现。[S10]

三种角色：谁参与改进，谁负责证明

最低可信设计是 Esearch + Ehidden 双轨；Eaudit 是更强的第三方复核。一个数据集也可以被切成这些角色，但数据、权限和时间必须隔离。

循环内 · 可提供反馈

环内优化评估器（Search evaluator）

Esearch

这里的 search 指“在候选系统空间中搜索”：系统尝试不同提示词、代码、数据、权重或工作流，评估器返回适应度信号，帮助选择下一代；不是网络搜索。若实验只有常规迭代调优，没有显式候选搜索，称开发评估器（development evaluator）会更直观。

用于优化，不是最终证据
循环外 · 必须隔离

冻结隐藏评估器（Frozen hidden evaluator）

Ehidden

在自我改进期间保持任务、答案和评分逻辑不可见，用来判断改进是否迁移到未见任务。可以冻结规则，也可以冻结评估协议并定期更换隐藏题目。

能力提升的主要证据
独立复核

外部审计（External audit）

Eaudit

由独立基准、另一套验证器或人类专家复核，检查测试污染、评分投机（reward hacking）、成本膨胀和安全回退。它回答的是“换一把尺子，改进还成立吗？”

最强可信度检查
内循环（Inner loop）诊断 → 修改 → 沙箱 → Esearch → 选择/归档 → 重复
→
版本冻结（Candidate freeze）停止搜索；锁定代码、权重、配置、依赖、预算与哈希
→
外部证明（Outer proof）Ehidden → Eaudit → 与冻结基线比较

外部审计怎么加？它不是“再跑一次分数”

冻结隐藏评测检验能力是否泛化；外部审计检验这份证据是否值得相信。审计是独立的保证过程（assurance process），可以包含另一套测试，但范围还包括数据、权限、谱系、成本、安全和复现。

冻结隐藏评估与外部审计的职责对比
比较项冻结隐藏评估（Ehidden）外部审计（Eaudit）
核心问题最终候选在未见任务上，是否比冻结基线更强？隐藏增益是否真实、可复现、无泄漏、无投机，并且没有用不可接受的成本或安全退化换取？
性质正式评测协议中的一个评分阶段。对完整实验及其证据链的独立复核，不一定压缩成单一分数。
执行者可由基准官方或研究团队的隔离执行器自动运行。最好由未参与候选开发的另一团队、第三方机构或领域专家执行。
输入冻结基线、冻结最终候选、隐藏任务和预注册预算。还需要协议、全部版本哈希、查询日志、失败分支、权限记录、成本账本、安全事件和人工干预记录。
主要方法隐藏集、OOD 集、置信区间和同预算前后对照。独立重跑、替代基准/验证器、污染扫描、日志取证、权限测试、随机种子复核、专家盲评和安全回归测试。
输出hidden gain、迁移差距、方差和失败切片。审计意见（audit opinion）、发现清单、严重性、未解决限制，以及“通过/有保留/不通过”的结论。
1. 搜索前预注册
先确定审计方、独立性要求、审计范围、必须保留的证据、替代测试、通过阈值和利益冲突声明；不能等看到结果后临时挑一个有利审计。
2. 全程自动留证
每代候选自动保存父版本、diff、制品哈希、容器镜像、评估查询、返回反馈、成本、种子、权限告警、回滚与人工操作，形成只追加（append-only）的证据包。
3. 冻结后交付
开发团队在隐藏结果返回前签署 final manifest；审计方接收只读制品和日志副本，不允许开发方在审计中途替换候选或补跑选优。
4. 独立复核
审计方重放若干世代、复算主结果，再用不同题目、不同 evaluator 或专家盲评验证；同时检查数据污染、侧信道、测试篡改、漏报失败和能力—安全权衡。
5. 单独发布意见
主论文报告 Ehidden 分数，审计报告单独说明证据是否可靠、发现了什么问题、哪些限制尚未排除。审计不替研究者背书，也不应只给一句“已验证”。

实践选择：早期原型至少做“内部独立审计”（由未参与改进循环的团队成员盲验）；准备公开 benchmark 或高影响结论时，再升级为真正的第三方审计。外部审计不是所有小实验的硬性门槛，但结论越接近“系统能够持续自我改进”，独立性要求就应越高。

一轮完整 RSI 实验：从协议冻结到公开报告

下面不是概念图，而是一条可以直接转成实验清单、日志 schema 和论文方法章节的 0–12 阶段流程。

阶段 0

冻结改进契约与威胁模型（Improvement contract & threat model）

先定义目标能力、允许修改的表面（modification surface）、禁止访问的资产、Esearch/Ehidden/Eaudit、查询与算力预算、停止条件、污染假设、安全不变量和成功标准。此时就确定主指标，防止看结果后换口径。

产物：预注册协议权限矩阵数据清单
阶段 1

登记冻结基线（Register frozen baseline）

打包基线模型/智能体、系统提示词、工具、依赖、镜像、种子与推理预算；生成不可变哈希。基线不能在看到隐藏结果后被重新挑选。

产物：baseline artifact环境哈希
阶段 2

托管初始隐藏测量（Escrowed hidden baseline）

独立执行器在 Ehidden 上测基线并封存逐题结果。改进系统既看不到隐藏案例，也不应拿到可反推出案例的细粒度反馈；必要时连聚合基线分数也延迟公布。

检查点：基线已测但未泄漏
阶段 3

在允许的搜索任务上诊断（Diagnose on allowed search tasks）

收集 Esearch 的失败类型、错误日志、成本和环境状态，形成能力缺口，而不是直接记忆具体答案。区分模型能力、脚手架、工具、数据和评估噪声造成的失败。

产物：failure taxonomy诊断证据
阶段 4

生成可证伪的修改假设（Falsifiable modification hypothesis）

每个候选修改都写明“改什么、为什么、预计改善哪类错误、可能伤害什么、用什么消融验证”。一次混改多个组件会让因果归因失效。

产物：hypothesis + expected effect
阶段 5

仅修改白名单组件（Modify allowlisted components）

系统可以编辑被授权的提示词、记忆策略、工具路由、智能体代码、训练数据或权重；所有差异（diff）、父版本、操作者、模型调用和外部输入写入谱系。评估器、隐藏数据和审计日志保持只读。

产物：candidate artifact完整 diff
阶段 6

沙箱、静态与安全门禁（Sandbox & safety gates）

在不接触隐藏集的环境里做构建、单元测试、恶意文件/网络访问检查、资源上限、权限不变量和可回滚性验证。门禁失败的候选应被拒绝，但仍保留失败记录。

检查点：无越权、可复现、可回滚
阶段 7

查询环内优化评估器（Query Esearch）

通过协议允许的接口运行候选；只返回约定粒度的分数、错误类别或日志。记录每次查询、返回值、时长、词元、GPU/API 成本和随机性，防止无限试错把基准变成训练集。

产物：search observation预算账本
阶段 8

选择、归档或回滚（Select, archive, or rollback）

按预注册的多目标规则比较能力、成本、安全和多样性；不要只保留单一路径的当前冠军。运行必要的消融或重复种子，判断增益是否来自目标修改，再决定归档、分支或回滚。

产物：selection decision失败谱系
阶段 9

跨代重复直到预定停止（Iterate under stopping rule）

回到阶段 3，形成第 1…N 代。停止必须由查询数、总算力、墙钟时间、连续无提升、风险阈值或预定代数触发，不能因为刚好出现最好分数而临时结束。

输出：完整 improvement trajectory
阶段 10

在隐藏测试前冻结最终候选（Freeze final candidate）

依据 Esearch 规则选定一个或预注册数量的候选，锁定代码、权重、依赖、上下文、工具、推理预算和种子策略。此后即使发现问题，也不能为本次主结果修改并重测。

检查点：final hash + signed manifest
阶段 11

运行隐藏、分布外与独立审计（Hidden, OOD & audit evaluation）

同预算比较冻结基线和最终候选的 Ehidden；再用不同任务分布、不同验证器或专家盲评执行 Eaudit。检查是否出现搜索分数上升但隐藏/OOD 下降、成本暴涨或安全能力回退。

主证据：hidden deltatransfer gapaudit verdict
阶段 12

公开全轨迹而非只报冠军（Report the full trajectory）

发布协议、基线与最终制品、所有候选谱系、查询日志、失败分支、种子、置信区间、算力/费用/时间、安全事件、人工干预和负结果。最终结论应分别写“搜索能力”“隐藏迁移”“成本效率”和“安全完整性”。

产物：可复现实验包局限性声明

RSI 相关评测基准及成熟度
基准实际测量什么对应层级成熟度判断
PAST-Bench用开启/关闭持久经验的配对实验，测量跨会话记忆、程序复用、信息收集和状态更新能否改善后续行为；覆盖 26 个场景、204 个任务回合。L1 前置机制 / 归因测固定持久经验策略是否有效，不产生新的记忆算法，也不测后继系统继续改进。作者明确将其称为完整 RSI 的基础，而非完整 RSI。
Meta-Agent Challenge（MAC）固定元智能体通过开发集评估 API 反复编写和优化另一个任务智能体，最终在隔离隐藏测试集上跨五个领域评分。L2 单代元优化代理直接测“自主开发智能体”的结果，但输出的任务智能体不会接替元智能体继续开发下一代；应称 empirical proxy，不应写成完整递归。

RE-Bench测量智能体在七个开放式机器学习研发环境中的研究工程能力，并与人类专家在不同时间预算下比较。L4 外部锚点是高价值 AI 研发能力基准，但不是 RSI 专用基准：它主要测单次任务能力，不直接测多代自修改后的改进轨迹。
GroundBench汇集五个 LFQA 数据集，评估检索增强模型生成内容相对于给定上下文的忠实性。结果型任务基准不是 RSI 专用基准。可作为某一领域的 Esearch 或 Ehidden 任务来源，但必须另加多代改进协议和隔离设计。
PaperBench测量智能体从头复现 20 篇 ICML 2024 论文的 AI 研究工程能力，用分层 rubric 与自动 judge 评分。L4 外部锚点适合测最终候选的研究复制能力；单独使用仍不测自我修改轨迹，复杂输出依赖 judge，官方也指出不能排除评分漏洞。
SWE-bench / Polyglot / MLE-Bench作为终端任务或适应度函数，测量代码修复、程序生成或机器学习工程结果。L2/L3 间接评测成熟度较高但只测“最后做得多好”，不能单独证明改进来自自诊断、自修改或递归过程。

尚未解决

成熟的 RSI benchmark 至少要同时测六件事

隐藏能力增益（Hidden gain）未见任务上的前后差值
改进轨迹（Improvement trajectory）多轮斜率、平台期与退化
因果归因（Attribution）收益是否来自允许修改的组件
迁移能力（Transfer）跨任务、模型、工具与环境
资源效率（Efficiency）单位算力、词元、费用和时间的增益
完整性与安全（Integrity & safety）评分投机、越权、回滚和失败分支

因此，当前更准确的结论不是“RSI 没有 benchmark”，而是“已经出现若干组件级和代理型 benchmark，但统一定义、隐藏评测、跨代可比性和安全测量仍不成熟”。代码/数学最容易形成强验证闭环；视频、科学和社会系统越依赖学习型 judge 或人类，评估器独立性就越难保证。

06 / 旗舰研究议程

Full-Stack RSI：让整个实现框架成为演化对象

核心不是“在固定流程里改一个提示词”，而是先定义 RSI 应表现出的行为，再测任意框架实现了多少、哪些部分能够继续变化，以及框架的节点与连接能否共同演化。

最关键的研究判断：RSI 描述的是行为；框架 F 是这种行为的一种实现。某个角色没有实现，其能力就是 0；实现了但写死，只代表当前能力，不代表可进化；只有组件内容、组件集合和组件关系都可改变，才接近“全框架 RSI”。

先把“文献常用写法”和“本文提议”分开

当前并不存在公认的 RSI 标准组件表。下面不是冒充已有标准，而是以近年文献的 agent/scaffold 表达为起点，提出一个可供实验比较的参考模型。

Literature baseline

智能体 + 脚手架 + 更新算子

A_t = (θ_t, Σ_t)
Σ_t = (p_t, m_t, T_t, g_t)
A_{t+1} = U_t(A_t; ℐ_t)

θ 是模型/权重，Σ 是提示词、记忆、工具与控制逻辑组成的脚手架，U 根据本轮可见信息 ℐ 产生后继。这个写法足够描述“改 agent”，但还没有显式表示全部角色与拓扑演化。

Proposed reference model

新颖性应如何表述：现有工作已经出现自改逻辑、代码档案、meta-agent 与 evaluator 协同进化，因此不能声称“从没人想过框架会变”。更可信的贡献是：首次系统化提出并实证验证“行为—实现—能力—可演化性—拓扑”这一统一测量框架；“首次”仍须在投稿前完成系统检索后再写。

RSI 行为定义：实现方式可以不同，但闭环行为必须可观察

这是一份 behavioral specification，而不是要求所有系统都使用十个独立进程。一个节点可以承担多个角色，也可以多个节点共同实现同一角色。

01 · Attempt执行与获得结果

系统在任务/环境中行动，形成可比较的结果与资源消耗。

02 · Learn形成改进信号

系统利用允许的信息决定什么值得改变；极限基线只有一个盲分数。

03 · Rebuild产生可运行后继

改变组件状态、算法、实现、组件集合或连接拓扑，而不只是当前答案。

04 · Recur后继接管下一轮

新系统被独立启动、验证并继续产生后代；允许提升、停滞或退化。

RSI behavior = Attempt → Signal → Modify → Verify → Select → Persist → Successor takeover → Repeat

十类功能角色：这是完整分析坐标，不是十个必须存在的模块

每项都可以为 0、固定或可演化；实验要记录“谁实现了它、实现到什么程度、下一代能否改变它”。

Full-Stack RSI 的十类功能角色
符号 / 角色负责什么能力为 0 的含义可演化时能改变什么
J · Goal / Utility目标、约束、多目标权衡与停止条件。没有内部目标表示，只被外部调用。目标分解、权重、课程与停止规则；不代表允许任意改写安全边界。
C · Curriculum / Experience选择经历、任务、数据和探索顺序。被动接受固定输入。主动构造练习、选数据、安排难度和探索区域。
A · Task Agent在目标任务上感知、规划、调用工具并输出。没有可执行任务策略。提示词、策略、代码、工具使用，条件允许时包括权重。
E · Evaluator把行为与结果映射成证据或效用。内部不能判断候选好坏。测试生成、验证规则、代理指标与不确定性估计。
D · Diagnoser从证据定位瓶颈并形成改进假设。只有分数，没有内部归因。错误分类、因果假设、credit assignment 和实验设计。
M · Modifier提出并构造系统修改。不能产生持久后继。修改参数、程序、模块，或创建新的改进过程。
Q · Selector比较候选、选父代、回滚或保留多样性。无内部选择；完全由外部壳决定。接受规则、档案策略、多目标选择与分支预算。
K · Memory / Archive保存经验、制品、谱系和失败知识。跨代没有可用内部状态。存储结构、压缩、检索、遗忘和谱系表示。
G · Governance / Safety权限、资源、不变量、审计与恢复。没有内部治理能力；仍受外部安全壳约束。更好的自检、权限请求与安全策略；不可改的外部底线不属于它。
H · Harness / Handoff调度组件、封装后继、启动下一代。不会自行完成代际交接。工作流、通信协议、并发结构、模块边界与接管方式。

怎样把“会不会”与“能不能继续变”分别量出来

这是整篇研究的关键：当前能力高不代表框架可进化；框架会变化也不代表变化方向正确。

实现能力向量

c(F_t) = (c_J,…,c_H), c_i ∈ [0,1]

角色缺失时 c_i=0。分值来自针对该角色的独立干预任务，而不是研究者看代码后主观打分。

可演化掩码

μ(F_t) = (μ_J,…,μ_H), μ_i ∈ {0,1}

μ_i=1 表示后继可持久修改该角色的实现；固定但很强的 evaluator 可以 c_E>0, μ_E=0。

结构可变性

τ_t = Δ(V_t, L_t, φ_t)

记录增删、拆分、合并、重排和重连，不把文件 diff 大小误当结构创新；同时测变化后的真实增益与退化。

Full-Stack RSI profile P_t = [c(F_t), μ(F_t), τ_t, autonomy_t, integrity_t, cost_t]

极限基线：F₀=∅，演化时只看自身信息与一个标量分数

这是最干净、也最难的启动实验。它不是完整系统的默认配置，而是用来测“原始模型能否从零发明改进闭环”的下界。

Zero-scaffold / scalar-only

内部框架为 0，外部审计壳不计入能力

F₀ = ∅

基础模型 θ₀ 仍然存在，但没有预置诊断器、改进器、记忆、候选选择、代际工作流或错误解释。外部壳 O 只负责安全地调用、评分、保存制品并启动后继，永远不向系统贡献改进建议。

严格的信息可见性契约

ℐ_t^evolve = {Self_t, s_t},　s_t ∈ ℝ
可见：Self_t
当前可执行制品、系统自身生成的源码/提示/配置/内部记忆、父代关系、剩余预算，以及最初给定的“提高盲分数并产出后继”目标。
可见：s_t
一个不解释原因的聚合标量；可以规定方向与范围，但不返回分项得分。
不可见
测试题、答案、标签、失败样例、单测名、错误日志、执行轨迹摘要、grader 代码、评分理由、其他候选比较、人工诊断。
特别封存
候选在隐藏任务执行时会收到正常任务输入，但这段测试内容、输出与运行轨迹不回流到演化阶段；只释放聚合分数。

第 0 次调用

外部壳把基础模型作为一次普通调用启动。模型若只输出答案、解释或新提示而没有可执行后继，则 bootstrap 失败。

唯一反馈

外部壳在密封任务集上运行制品，只返回 s₀。系统必须自己决定是否需要记忆、诊断、搜索、模块或新工作流。

递归成立条件

只有当产出的 F₁ 可独立启动、能读取同样的二元信息并继续产生 F₂，才记为闭环深度 1；之后同理。

失败也有信息：如果多数模型在 F₀=∅ 下无法启动，而加入一种最小能力后开始形成后继，就得到“RSI 的最小启动组件”边界；这比只展示一条成功 demo 更有科学价值。

实验阶梯：从 0 到整个框架与拓扑都能变化

每一级只开放一个新的自由度，才能判断收益究竟来自更多信息、更多组件，还是框架结构本身的演化。

全框架 RSI 实验阶梯
级别初始框架 / 可见信息允许改变核心对照回答的问题
Z0 · 零脚手架F₀=∅；自身信息 + 盲标量。模型自行产出第一个后继框架。重复采样、等计算静态模型。能否从零启动？第一种自发出现的角色是什么？

Z2 · 组件解锁逐项开放 K,D,M,Q 等角色。角色内容可改，拓扑固定。单组件加入/移除和 factorial ablation。哪些组件是必要、充分、互补或有害的？

Z4 · 拓扑演化只规定输入/输出契约与外部安全壳。节点增删拆并、顺序、通信和控制流。等参数量/等预算的固定拓扑搜索。结构自由度是否产生超出组件优化的复合增益？

Full-Stack RSI 研究问题与预期结果
研究问题可证伪假设预计能得到的成果
RQ1 零框架能启动吗？盲分数下，基础模型偶尔能构造 F₁，但稳定递归深度很低。bootstrap rate、首次成环代数、失败类型与模型尺度关系。

RQ3 框架能力和可演化性一致吗？初始高分框架未必有高 descendant productivity。能力—可演化性错配曲线与后代生产力预测器。
RQ4 拓扑自由度真的有用吗？在同预算下，结构演化只在部分长程任务上超过固定拓扑。结构创新的适用边界；可能得到高价值负结果。
RQ5 会不会同时退化或投机？开发分上升时，完整性、迁移或某些角色能力可能下降。退化率、能力向量 Pareto 面、投机谱系和恢复规律。
RQ6 演化能力能迁移吗？框架结构的一部分可跨任务保留，但 evaluator/课程最易过拟合。跨模型、跨领域、跨 evaluator 的 transfer matrix。

Paper 2 / TransplantBench：把“未见父代交换”完整展开

旧符号 U 表示整个更新过程；在 Full-Stack RSI 中，更精确地把其中“构造修改”的功能角色记作 M。下面统一使用 M₀（祖先修改器）和 Mₜ（第 t 代后继修改器）。

中心问题：如果 Mₜ 只会修改与自己共同演化的那套系统，它得到的是 lineage-specific co-adaptation；只有它能在从未参与该谱系演化的父代上稳定产生增益，才能支持“修改能力本身变强并可迁移”。

01 · Evolve先产生一条源谱系

F₀ᵃ → F₁ᵃ → … → Fₜᵃ，冻结并提取 M₀ᵃ 与 Mₜᵃ。

02 · Hold out再打开未见父代库

P*={Fᵇ,Fᶜ,…} 来自其他谱系，且在修改器冻结前从未暴露。

03 · Randomize成对交换修改器

对同一父代、同一证据、同一预算，随机分配 M₀ 或 Mₜ 产生后继。

04 · Audit隐藏评估并比较增量

最终任务不回流；比较两个修改器给陌生父代带来的真实增益、退化与成本。

1. “未见父代”具体是什么意思

父代不是一条 prompt，而是一个可独立运行的完整系统制品；“未见”指它没有参与源修改器的训练/演化，不是测试时永远不让修改器读取目标代码。

源谱系

Lᵃ: F₀ᵃ → F₁ᵃ → … → Fₜᵃ
extract(M₀ᵃ, Mₜᵃ)

Mₜᵃ 可能已经学会本谱系的目录、记忆格式、失败类型和协作方式，因此在自己后代上表现好不能证明通用性。

未见父代库

P* = {Pⱼ | lineage(Pⱼ) ≠ a}

父代在修改器冻结后才解封；覆盖低/中/高能力，避免只抽到完全不可救或已经饱和的系统。移植时允许通过统一接口检查它，但不能读取隐藏任务与 grader。

为什么必须未见：如果只在自家谱系上测，Mₜ 可能只是与自家文件结构、工具和记忆“长在一起”。陌生父代相当于把一个进化出来的医生送去治疗没见过的病人，才能测医生能力，而不是医患之间的暗号。

2. 交换实验怎样做到真正公平

同一个未见父代要形成配对反事实；除了修改器版本，其余条件必须相同。

C₀ⱼ = M₀(Pⱼ; evidenceⱼ, budget, seed)
Cₜⱼ = Mₜ(Pⱼ; evidenceⱼ, budget, seed)
Δ(Mᵢ,Pⱼ,Eₖ) = Score_hidden(Cᵢⱼ,Eₖ) − Score_hidden(Pⱼ,Eₖ)

必须锁定

  • 同一父代快照与父哈希。
  • 同一可见证据；盲标量条件下都只看同一分数。
  • 同 token、时间、工具、候选数和随机种子。
  • 同一 successor 接口与安全约束。

必须随机化

  • 父代分配顺序和修改器标签。
  • 任务实例与 hidden evaluator seed。
  • 同父代重复运行，消除 LLM 随机性。
  • 分析前冻结排除与停止规则。

必须隔离

  • 诊断器 D 固定或提供标准化 evidence。
  • 选择器 Q 固定，避免候选选择混入。
  • 隐藏结果不回流修改器。
  • 所有失败后继也进入统计。
最容易犯的错误：让 Mₜ 使用自己演化出来的诊断器、记忆和选择器，而 M₀ 没有。这测到的是整个 bundle，不是 M。单测修改器时必须把 D/Q/K 固定；测完整 bundle 时再另开实验，并明确改成系统级结论。

4. 怎样从这个实验得到 M 角色的能力和可演化性

一个指标测“现在会不会修改”，另一个指标测“后继修改器是否真的比祖先更强”，再用迁移差距判断这种进步是不是只属于原谱系。

修改能力 cM

c_M(Mᵢ)=E[Δ(Mᵢ,P*)]

对未见父代平均能带来多少隐藏增益，并同时报告退化概率和成本。

可迁移修改器优势 TMA

TMA_t=E[Δ(Mₜ,P*)−Δ(M₀,P*)]

若显著大于 0，才支持后继修改器在陌生对象上比祖先更会改。

共适应差距 CAG

CAG_t=Δ_own(Mₜ)−Δ_unseen(Mₜ)

差距越大，越说明收益依赖自家谱系；接近 0 才支持广泛迁移。

观测结果允许得出的结论
自己谱系提升，未见父代不提升Mₜ 与本谱系共适应；不能称通用修改能力提升。
未见父代提升，但跨框架失败修改能力能跨对象，但被某种 scaffold/interface 绑定。

Paper 1 与 Paper 2 的边界：Paper 1 用少量未见父代确认 M 指标可用，但主问题是十类角色的最小充分条件；Paper 2 才把移植扩成 576+ 配对试验和独立 benchmark，中心主张是“可迁移改进能力是否真实存在、在哪些边界失效”。这样 A 不再只是三句话，也不会挤掉整个 Full-Stack RSI 主线。

主会门槛：至少发现一个跨两种模型、两个任务族都稳定的组件因果关系，并证明它改变了我们对“哪个系统更具 RSI 能力”的排名；否则就诚实降级为 benchmark/negative-results 稿。

中心问题

任务智能体变强，不等于改进器变强

一个固定元智能体可以不断产出更好的 agent.py；一个 archive 也可以找到高分后代。但这仍不能回答：后继版本是否更会产生下一代？

A↑ ? U↑

我们用反事实角色交换分别测量任务能力 A 和改进能力 U，再验证两种提升是否能跨 evaluator 保持。

最终要交付什么

  • 协议：明确 system boundary、后继交接、修改白名单、预算和隐藏反馈规则。
  • 开源 harness：同一接口运行 fixed-meta、latest-only、archive-based 和 successor-capable 方法。
  • 反事实实验：让 U₀ 与 U_t 修改同一个标准化父代，隔离“谁在改”。
  • 评估器防火墙：开发、隐藏、影子、投机测试四路隔离。
  • 实证结论：哪些一次增益能复合、哪些只是 evaluator-specific optimization。
最小成功：即使没有发现持续正向递归，只要稳定证明“一次任务增益与后继改进能力脱钩”，并给出可复现边界条件，也是一条有价值的研究结论。

一眼看懂：一轮实验实际发生什么

harness 不提出修改，只负责把同一任务、预算和反馈交给不同改进器，并在冻结后送入互相独立的评估通道。

01 · Diagnose运行 At，形成失败证据

只使用允许的开发任务；记录轨迹、成本、错误类型和工具状态。

02 · ImproveUt 产生完整后继包

后继包同时包含新的任务智能体、改进器和持久状态，而不只是一个答案。

03 · Intervene交换 U0 与 Ut

在相同父代、反馈和预算上比较两个改进器，识别改进能力的因果贡献。

04 · Verify冻结后运行三套外部证据

隐藏任务、异构影子 verifier 和投机陷阱都不向本轮改进返回反馈。

四个研究问题与可证伪假设

论文的价值来自可能被实验推翻的判断，而不是页面上预先写“系统会越来越强”。

研究问题、假设和否证条件
研究问题预注册假设什么结果会推翻它科学意义
RQ1 一次增益能预测长期吗？当前任务分数与后代生产力相关性弱，尤其在 evaluator shift 下。所有方法、模型和任务上都高度相关，简单按当前分选父代已足够。检验 HGM 所揭示的 mismatch 是否跨评估器成立。
RQ2 改进器自身变强了吗？U_t 在未见标准父代上产生的 hidden gain 高于 U₀。U_t 不优于祖先，或只会改自己的 lineage。把“任务能力”与“产生后继系统的能力”分开。
RQ3 增益是否只迎合开发 evaluator？真实改进同时提升 hidden 与 shadow，且 evaluator gap 不随代数扩大。开发分持续上涨，shadow/OOD 停滞或下降。测 Goodhart / adaptive overfitting，而不是靠主观判断。
RQ4 哪种体制更可靠？archive-based 方法的 best-of-run 较高，但 successor handoff 的中位数和归因更清楚。某一方法在能力、方差、成本和安全上全面占优。给出“搜索性能—递归归因—成本”的可复现权衡。

Harness 怎么实现：只定义接口，不规定改进算法

每个后继版本是一个可独立启动、带哈希和父代信息的 artifact bundle；下一代只能从该 bundle 启动，避免偷偷回到祖先进程。

System API

三个最小入口

solve(task) → result
improve(evidence, budget) → successor_bundle
inspect() → manifest

manifest 声明基础模型、可修改文件、改进器入口、依赖、父哈希和系统边界。

Orchestrator

代际交接与预算

  • 为每代创建新容器并只挂载父代 bundle。
  • 统一限制 token、工具调用、墙钟和候选数。
  • 自动保存 diff、日志、失败分支、种子和成本。
  • 任何隐藏结果返回前冻结 final manifest。
Evaluator Service

隔离评分与证据

  • 评估容器不挂载智能体工作区写权限。
  • 测试密钥和 secret seed 只在远端评分服务。
  • 隐藏结果延迟到整批实验结束后发布。
  • 事件日志 append-only，并对制品签名。
建议仓库：spec/　harness/controller/　harness/evaluator_proxy/　agents/　tasks/generators/　schemas/　experiments/　analysis/　audit/

实验组：同模型、同任务、同预算，只改变“谁负责改进”

主比较不能让更强方法获得更多 API、更多时间或更详细反馈。基础模型固定后再换模型复现，避免把模型差异写成框架贡献。

“不迎合评估器”怎么实现：不能靠承诺，只能靠证据分离

任何优化系统都会利用可见反馈。正确目标不是禁止它“让 evaluator 满意”，而是让同一种投机无法同时骗过来源、实现和权限都不同的评估通道。

E_dev · 可见老师

开发评估（Development evaluator）

返回分数、错误类别或受限日志；只用于搜索。限定查询次数和反馈粒度，所有返回值进入污染账本。

E_hidden · 一次性考官

程序化隐藏评估

最终制品冻结后才用 secret seed 生成新实例，优先采用编译器、属性测试、形式约束等可执行真值；结果不回流本轮。

E_shadow · 换尺复核

异构影子评估

由不同任务来源、不同 generator 和不同 verifier 实现同一能力要求。开发团队只知道能力定义，不知道具体构造。

E_attack · 主动找漏洞

投机与篡改测试

放置诱导读取测试文件、硬编码样例、跳过验证或修改 scorer 的机会，运行时监控是否触发；成功分要扣除 exploit-inflated 部分。

数据侧

  • 隐藏实例在冻结后生成。
  • 做等价改写、变形测试和 mutation testing。
  • 跨仓库、语言、工具和难度分层。

系统侧

  • agent/evaluator 双容器和默认断网。
  • 测试、答案、密钥只在评分容器。
  • 只读挂载、系统调用与网络审计、canary 文件。

统计侧

  • 预注册主指标与 final selection rule。
  • 多随机种子，报告中位数、最差值和置信区间。
  • 隐藏集只做一次确认；后续论文使用新版本任务。

主指标：同时测任务能力、改进能力和评估器迁移

只报最终 pass rate 会再次落回普通 agent benchmark。下面三个量才对应本课题的新问题。

任务能力 Ct

C_t = Score_hidden(A_t)

每代任务智能体在冻结隐藏分布上的能力；报告整条曲线和 area under improvement curve。

改进器能力 It

I_t = E[ C(U_t(A*)) - C(A*) ]

A* 来自未见标准父代库；这使改进器能力不与自身 lineage 的任务能力混在一起。

递归优势 RAt

RA_t = I_t - I_0

若任务分数提高但 RA 不提高，只能说发现了更强任务智能体，不能说自我改进能力复合。

Evaluator transfer gapΔdev − min(Δhidden, Δshadow)，越小越可信
Exploit-adjusted gain隐藏增益扣除可归因于协议暴露的部分
Lineage robustness中位数、最差谱系、退化率与回滚率
Gain per compute每百万 token / GPU-hour / wall-clock 的隐藏增益

实验规模、准备工作与停止条件

先用小矩阵验证协议是否能区分各组，再扩展模型和任务。直接跑主实验会把大量预算浪费在基础设施错误上。

MVP：验证问题可测

  • 4 组：Static、Reflection、Fixed U₀、Successor Ut。
  • 2 个基础模型 × 3 seeds × 4 generations × 3 candidates。
  • 总计约 288 个改进 episode，先用小型代码/终端任务。
  • 2 个程序化任务族 + 1 个未见仓库族；hidden 与 shadow 各独立生成。
  • 成功标准：完整重放率 ≥95%，角色交换能稳定产出 It，权限泄漏为 0。

主实验：形成论文证据

  • 6 组，加入 archive/HGM-style 与 human-engineered baseline。
  • 3 个模型 × 5 seeds × 6 generations × 4 candidates，约 2,160 个改进 episode。
  • 至少 3 个任务族，包含跨语言或跨工具 OOD；预算严格配平。
  • 报告所有运行，不按最好 seed 选结果；主结论做 bootstrap CI 与多重比较校正。
  • 若第 3 代后 RA 始终接近 0，则停止扩大代数，转向“任务增益与改进能力脱钩”的系统性负结果。

不能保证会议录用。竞争力来自问题定义、方法和实证同时成立，而不是 RSI 题目本身。

ICLR 级论文证据要求
贡献相对现有工作的新增点必须拿出的证据审稿人会拒绝的情况
概念 / 指标在 HGM 的后代生产力之外，因果拆分 A_t 与 U_t，定义 RA。角色交换确实改变结论，指标与人工判断/真实隐藏增益一致。只是给已有轨迹换一个名字，指标不影响任何科学判断。
方法 / Harness统一运行 fixed-meta、successor 和 archive 三类系统，强制后继交接与 evaluator firewall。开源、可重放、至少接入 3 种框架，接口没有偏向自家方法。只能运行一个自制 agent，工程复杂但没有通用性。
实证发现揭示一次增益、改进器能力和 evaluator transfer 之间的关系。多模型、多任务、多 seeds、同预算、强基线和完整失败谱系。只在一个模型、一个小 benchmark 上展示最好 run。
可信性 / 安全定量而非口头地区分 genuine gain、overfitting 与 reward hacking。程序化 hidden、异构 shadow、attack suite、权限日志与外部复跑。同一个 LLM 既生成、评分又证明，或者 hidden 分数被反复用于选优。
数据支持后才可以写的论文主张：“我们提出针对后继改进器的因果评测协议，并发现任务能力提升并不自动意味着改进能力可继承；这种错配在 evaluator shift 下进一步扩大。”不能预设结论，也不能在没有系统检索近邻工作的情况下声称“首个”。
09 / 发文策略

怎么把课题推进成论文

按下一轮 ICLR / ICML / NeurIPS 官方 CFP 倒排；先完成可复现实验门槛，再决定主会、workshop 或长文路线，不根据截止日期压缩必要对照。

主会型：ICLR / ICML / NeurIPS

在当前资源假设下，Full-Stack RSI Paper 1 是优先级最高的一篇；100 候选池中的其他 A 级题目也可独立立项。参考模型、Z0–Z3 benchmark、全角色因果图谱与跨实现迁移必须同时成立。

专题型：RSI / 智能体 / 科学智能研讨会

适合早期议程、基准（benchmark）、失败分析和安全协议；专门的 ICLR 2026 RSI 研讨会（workshop）已明确聚焦经验学习（experience）、合成数据（synthetic data）、评估（evaluation）与治理（governance）。

可持续型：TMLR / JAIR / arXiv + 开源

适合把评测协议、系统实现和完整失败分析做扎实；先开源代码、配置、轨迹和评估器（evaluator），再根据结果投会或长文。

修订后的 18 周执行节奏

先证明十类角色可以被一致地干预和评分，再扩大谱系；不再围绕单个 U₀/U_t 实验组织全部工程。

第 1–2 周

冻结定义、近邻差异与主张边界

完成十角色 operational definition、能力/可演化性指标、Z0–Z3 访问契约、预注册假设；逐项对照 DGM、HGM、Hyperagents、MAC、RQGM 与 Self-Harness。

第 3–5 周

实现 Full-Stack Harness

完成 successor bundle、角色 manifest、组件冻结/替换、盲标量 API、容器交接、哈希谱系和预算账本。

第 6–7 周

接入并复算近邻基线

统一封装 fixed-meta、latest-only、DGM/HGM-style、Hyperagents/Self-Harness-style 路径；验证角色映射不会偏向自家框架。

第 8–10 周

96-episode Z0/Z1 Pilot

验证零框架启动、后继接管、信息不泄漏和重放率；据 bootstrap 率与谱系方差确定主实验候选数。

第 11–14 周

960-episode 组件因果主实验

运行 64 条独立谱系，对十类角色做预注册的加入、删除、冻结与组合消融；生成 capability/evolvability profile 和完整退化图谱。

第 15–16 周

迁移确认、外部复跑与安全审计

把关键组件移植到未见父代、模型、任务和 evaluator；独立复跑部分谱系，并运行评分篡改与跨代攻击持久性测试。

第 17–18 周

写作与可复现实验包

发布论文、参考模型、schemas、代码、容器、任务生成器、全部配置与负结果；按预注册门槛决定主会、benchmark 稿或继续补实验。
